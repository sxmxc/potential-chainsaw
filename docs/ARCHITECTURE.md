# Architecture rules

## Shared construction and simulation

- `scenes/construction_workspace.tscn` owns the shared World, ConstructionSession, WorkspaceHUD and authoring drawer. It binds tools, context presentation, simulation actions and scenery import. `scenes/world.tscn` and WorldManager retain the shared BuildManager, SimulationManager and cameras. The standalone workspace needs no GameManager or main-menu nodes.
- BuildManager owns placement, connector snapping, selection, configuration and snapshot history. Validate complete proposed edits before committing. Group edits are atomic; one forbidden member rejects the whole operation.
- SnapManager owns one candidate/validation path: exposed compatible track connectors, cursor-directed physical surface hits for scenery, then grid fallback. Surface hits select the target; measured occupied volumes and world-space edges decide rigid attachment without changing rotation. Edge-adjacent faces are alternatives, Tab chooses deliberately, and short hysteresis stabilizes the default. Two-pixel ray sampling handles exact silhouette misses. BuildManager preserves the actual grab-plane height and offset for direct dragging. Both preview and commit validate the complete group.
- Construction history uses Godot's `UndoRedo` with complete layout snapshots. BuildManager registers validated edits without replaying them; undo/redo restores selection by stable IDs. UI and mode resets use the engine's history API.
- `BuildingPiece` is the common placed-object node for tracks and scenery. PieceDefinition resources own catalog metadata, connectors, bounds and thumbnails. Changing an adjustable piece must update its geometry, collision, connectors and placement bounds together. Reject conflicting changes without leaving partial state.
- PieceDefinition also owns `normalized_configuration` and `configured`: ordinary definitions retain their geometry; ElevatorDefinition and SupportDefinition derive instance geometry without changing shared resources. BuildingPiece, save loading and puzzle validation call the resource directly. SupportDefinition supplies the matching model sections to the support scene.
- SimulationManager owns the live marble set, pause/reset, completion and signal propagation. MarbleRelease owns its schedule and physical spawning; MarbleCollector owns its authored detection area. Other behaviors use collision, forces and impulses. Collector deliveries and behavior outputs determine success; a reference solution is never the completion test.
- `BuildingPiece` discovers all `PieceBehavior` nodes in its authored model scene, including the root. Components own configuration, enabled state, gameplay, ports and reset. `start_run` starts a run; SimulationManager changes `active` on pause/resume/end. Static pieces have no behaviors. Supports, releases, collectors, fans and mechanisms all use this same lifecycle.
- PieceDefinition's `behavior` is a catalog tag, not a constructor selector. Its scene and exported behavior nodes select functionality. Native collision scenes retain their authored shapes; ordinary GLBs and adjustable support sections use common mesh collision generation. Configuration refresh recollects visuals/collision without creating duplicate bodies. No central gate/sensor/fan factory or runtime box-building helper exists.
- Behaviors declare `inputs` callbacks, pulse `outputs`, and persistent `state_inputs`/`state_outputs`. BuildingPiece derives its input/output owner maps without relaying events and owns pulse/state compatibility queries. The wiring UI and BuildManager use those queries for both available choices and committed links. BuildManager validates component declarations and the authored wiring for simulation start and puzzle publication; SimulationManager only delivers signals during a run. Port names are unique across the piece's components; links retain their saved `event`, `target`, `action` fields.
- SimulationManager processes outputs with a FIFO queue, in emission and saved link order. Receiver outputs continue downstream rather than being suppressed. Persistent values emit only changes and restore their initial state on reset; start seeds state connections. Non-settling propagation is bounded at the scene-configurable delivery limit (16,384 by default) per transaction and stops simulation with a wiring error. No competing bus, runtime piece index or recursive dispatcher exists.
- Pause suspends mechanism motion and release scheduling. Reset clears runtime state and restores configured initial state while preserving construction.
- Marble owns its temporary capture state and the physics snapshot restored on release. Each elevator bucket holds its marble directly; simulation pause reads the same capture state. Restore its collision and freeze state on release or reset; discharge above the output track and let physics carry it onward.
- The menu showcase has its own SubViewport and World3D. It must not modify the playable world's construction or saves. Its camera animation lives in the saved scene.
- GameManager switches menu/world music on mode transitions. World also appears in the showcase, so scene `_ready()` must not start its playlist.

## Puzzle rules and persistence

- ConstructionSession owns the typed Sandbox, Authoring, Puzzle Play and Player Test contexts, personal track identity and persistence, puzzle drafts/publication and isolated player-test baselines. Context changes clear the previous simulation, rules, authoring permission, scenery, gestures and history; the workspace resets context UI and wiring. `context_changed` means a transition; `changed` refreshes metadata/progress without navigating. Sandbox is unrestricted; Puzzle Play and Player Test use the same PuzzleRules. Active construction tools belong to BuildManager and running/paused/result state belongs to SimulationManager. The World's saved `PuzzleBoundary` mesh node owns boundary display and the editor's two-corner drawing gesture; authoring controls call it directly. It observes session mode changes and leaves puzzle persistence and transitions to ConstructionSession.
- Inventory is derived from the current layout. Duplication consumes stock; deletion and undo restore it. Permissions and boundaries apply to complete edits, including configured dimensions and mechanism links.
- Keep authored starting layouts separate from player constructions and reference solutions. Returning from Test as Player restores the authored baseline.
- PuzzleStore owns the shared versioned JSON loader, definition validation, publication and validation fingerprints. Official content is registered by `resources/campaign_manifest.json`; local published and imported community content never override that registry. Drafts, published puzzles, imported community puzzles and community completion records use separate user paths. Bundled levels live in `resources/campaign/`.
- PuzzleStore validates authored records directly, without passing puzzle data through the personal-track loader. Publication and community import additionally check the reference against PuzzleRules; drafts can retain an obsolete reference while being edited and retested. SavePaths owns filename-safe IDs for both persistence formats.
- Chapters are data-driven through `resources/campaign_chapters.json` and campaign-manifest registrations. Draft-only `campaign` metadata holds chapter, ordering and prerequisites; ordinary published JSON omits it. Introduction is optional and never gates main chapters. CampaignDefinition owns chapter grouping, unlocks, resume and Next queries over one loaded campaign. Queries receive current progress explicitly, perform no file I/O and never mutate route state. PuzzleStore.load_campaign loads registration/content once; the browser retains that definition for its displayed list. PuzzleStore alone writes completion and route state, including advancement to an empty chapter. Preserve flat completion records by stable puzzle ID; store route/resume state separately in `campaign_state.json`.
- Marble Engineer has one construction system: BuildManager places and edits tracks and environment instances with the same previews, selection, rigid group transforms and history. PieceDefinition determines connectors and collision behavior; modes and PuzzleRules determine permitted operations. Registered scenery uses imported models and the same generated mesh collision as other pieces; its definitions are authoring-only. Explicit scene composites retain their authored native collision. ConstructionSession loads gameplay scenery as fixed geometry outside player construction.
- Construction records and history snapshots use the same `piece` ID, transform and configuration fields for tracks and scenery. `PuzzleEnvironment` converts registered scenery placements at the puzzle boundary. Puzzle JSON stores catalog `asset`, `uid`, position and quarter-turn rotation in `environment_instances`; there are no scene references, composite placements or publication snapshots. Authoring edits scenery through shared construction, while player modes instantiate the same catalog scenery as fixed objects outside inventory. Both publication destinations use the same definition and solution validation. Retired scene fields are rejected before resource loading.
- Publishing requires a successful physical test matching the current authored definition. Content changes invalidate that proof. Revisions retain stable puzzle IDs.
- Preserve existing track-save compatibility. Mechanism links use stable piece IDs, survive saves, remap within duplicated assemblies and are removed when their targets are deleted.

## Native scenes and UI

- Construction and camera input defaults are authored in `project.godot` through Godot's Input Map. Godot loads actions before scenes enter the tree; workspace startup never installs or resets them. ConstructionInput reads these defaults for settings overrides and restores only the game's actions, preserving engine/addon actions. Saved bindings remain InputEventKey overrides in `settings.cfg`.
- Main owns application navigation, the campaign browser, completion window and personal-track/settings dialogs. GameManager guards unsaved navigation and hosts the workspace; it does not load construction, own track identity or start player tests. ConstructionWorkspace binds its authoring drawer into the shared HUD's saved context slot and routes context actions. WorkspaceHUD binds shared tools and presentation. FileToolbar and PuzzleBar emit actions rather than coordinating session transitions. Puzzle UI reads ConstructionSession and uses signals for application-level requests; it never reaches through a session to GameManager or HUD internals. Layout remains in saved scenes.
- Keep presentation in saved `.tscn` scenes and the shared `resources/sandbox_theme.tres`. Scenes must be inspectable and previewable before `_ready()` runs. Do not generate scene files at runtime.
- The selection inspector owns object settings, capability descriptions and player permissions. The shared Connect tool owns visual mechanism link authoring; a separate overlay toggle shows directional links during normal building. The contextual toolbar owns ordinary object actions. Puzzle authoring owns only definition-wide settings, inventory, boundaries, objectives and publication; it has no alternate object or link editor. Reusable scenery scenes enter the toolbox's normal placement preview.
- Behavior scenes own exported `configuration_fields` arrays of PieceSetting resources. PieceDefinition reads those same saved resources through SceneState, including inherited scenes and nested instances, for normalization, defaults and authoring constraints. MechanismSettings renders them; there is no name-keyed settings table or UI-specific capability list. Configuration still commits through BuildManager permissions, validation and history. Saved overrides remain separate from resolved runtime defaults.
- UI scripts bind data, connect signals and update visibility, enabled states and Theme variations. Keep game logic, persistence, physics, snapping and history out of presentation code.
- Ordinary controls and StyleBoxes belong in saved scenes and the Theme. Dynamic lists instantiate reusable saved widgets such as `piece_card.tscn`.
- Containers own internal layout; anchors position outer panels. Layout minimum sizes live in scenes. Reusable fonts, colors, spacing and control states live in the Theme, rather than per-node overrides.
- Use the project-wide Theme and explicit shared Theme references in reusable scene roots. Preserve the selected fonts. See [UI design](UI_DESIGN.md) for interaction and visual rules.

## Resource registries

YARD's `resources/registries/piece_registry.tres` is the authoritative piece catalog. It scans `PieceDefinition` resources in `resources/pieces` and indexes `category` and `behavior`. Registry string IDs must match each definition's persistent `id`, including the existing `environment:partition`, `environment:deck`, `environment:column` and `environment:machine` IDs. Auto-scanning preserves existing registered IDs; when adding a resource, give its registry entry the same ID as the definition. See the installed [YARD documentation](../addons/yard/README.md) and in-editor `Registry` class reference.

The installed addon automatically rescans and rebuilds configured property indexes on editor Play and export. Its manual Reindex button is disabled; the README's manual reindex instruction is outdated for this installation. Headless runtime/GUT invocations consume the saved registry and do not invoke the editor's build hook. Tests should use the saved index rather than add a custom reindexing runner.

`PieceCatalog` loads entries through `Registry.load_entry` and queries through `Registry.where`; it owns presentation sorting. Category names and membership come exclusively from registered definitions. The toolbox shows those categories alphabetically with an additional All pieces option; there is no hardcoded category list or preferred order. Toolbox category filtering uses the property index, while inventories, extension choices, persistence and construction all resolve the same registered definitions. Support assemblies resolve their hidden sections through the same registry. There is no runtime directory scan, separate environment catalog or duplicate ID lookup table. Scenery definitions are saved resources referencing imported models, with measured solid metadata for placement and the common mesh-collision pipeline for physics. Unregistered IDs are rejected; there is no dynamic scene-definition cache. Keep mode permissions and native geometry in their existing systems.

## Checks and generated output

Use GUT from the Godot bottom panel or `godot --headless --path . --script addons/gut/gut_cmdln.gd -gexit`. `.gutconfig.json` discovers native GUT suites in `tests/`. Fixtures isolate tracks, puzzles, campaign progress, and settings in unique `user://gut-tests/` directories and clean them during teardown. Tests assert behavior; they do not force compiler warnings, publish levels, or rewrite bundled resources. Never redirect `APPDATA` or copy project caches for tests. Generated evidence does not belong in `docs/`.

Use the existing Godot editor for scene changes and live checks. Keep one editor per project. Review UI changes at small and large viewport sizes and exercise the affected interaction, rather than relying on source inspection alone.

## Visual mechanism wiring

`BuildManager.connect_mode` suspends construction gestures and shortcuts. MechanismWiring draws one large handle per sending/receiving role. Dragging accepts a whole compatible piece, highlights its projected bounds, and selects ambiguous compatible ports through a compact saved relationship card. Its independent Wires toggle leaves ordinary construction available and permits inspecting a curve. Selection emphasizes related links; directional arrows and endpoints show source-to-receiver flow. The inspector separates behavior settings from connection counts and its Connect action.

Link creation, modification and deletion call `BuildManager.edit_link`, which validates the actual ports and pulse/state compatibility before using ordinary configuration permissions, puzzle rules and snapshot history. Undo restores stable IDs and the active Connect tool. Duplication remaps internal links. Simulation hides wiring and restores the tool/overlay preference on reset. There are no persistent wire nodes or a second dispatcher.

See [Piece authoring](PIECE_AUTHORING.md) for scene/resource editing, the behavior lifecycle, signal semantics and extension examples.
